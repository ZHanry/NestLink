# NestLink Android

This is the new `com.zhanry.nestlink` Compose application. Android 11/API 30 is the minimum supported version; Android 10/API 29 is outside the target scope. The recorded API 30–36 x86_64 emulator baseline passed its then-current 3 instrumentation tests at each API level (21/21 total). The newer capture-layout, explicit source binding, resize and viewer changes compile; a fresh emulator run against the current JNI libraries is still pending. The APK packages Rust libraries for ARM64 and x86_64, but ARM64 physical-device behavior remains unverified. The management path connects through `nestlink-sdk`; Android can register a host-capable device and request explicit MediaProjection consent. Its foreground service can hold the user-granted one-use token while waiting, but it does not create a virtual display or read pixels until Rust app-core reports a connected session for this installation in the host role with a validated `View` permit. If that authorization ends, Android detaches the display surface and destroys the encoder; the same single display remains idle until the service stops or authorization returns. API 34+ content resize callbacks and API 30–33 display-rotation changes now retire the old layout, discard queued video, and reuse the same VirtualDisplay with a newly bounded reader and encoder. Raw content geometry changes advance the layout epoch even when even-dimension scaling preserves the same encoded size; exact duplicate callbacks remain idempotent. Real system-consent, projection-revocation, rotation and Android 14+ single-app resize acceptance are still outstanding. Host-session authorization, Android encoded-frame submission, and controller-side display are wired through app-core; end-to-end host/controller behavior on physical devices remains to be verified. Controller input and explicitly enabled Accessibility input adapters are wired in source and await current JNI/APK and device verification. Service registry management is available; Android manages services hosted by other devices and does not run the native public service host.

The controller-side viewer now polls source-0 layout and frames from app-core only while the Remote screen is resumed, rechecks the authorized layout after pixel conversion, and clears its image when authorization or session state changes. Decoded input is limited to 64 MiB per raw BGRA frame; that is not a total Java or process-memory limit. Android scales displayed images to a maximum 1280-pixel edge and tracks at most three display bitmaps. A rendered bitmap is recycled only after Compose releases its display lease and a hardware frame commit confirms the removed image is no longer submitted; if the view is detached or cannot provide that barrier, its bitmap stays bounded and unrecycled until a later attached frame can confirm retirement. Frames rejected before publication are released immediately. Android host capture sends encoded frames through the native host session. End-to-end host/controller behavior on physical devices remains to be verified. Controller input and explicitly enabled Accessibility input adapters are wired in source and await current JNI/APK and device verification. Service registry management is available; Android manages services hosted by other devices and does not run the native public service host.

The installation signing seed is encrypted with an AES-GCM key held by Android Keystore. The seed is passed to Rust only for the process lifetime and is never saved as plaintext. Account passwords, access tokens and refresh tokens are not persisted. Connect using the server origin and account password. HTTPS discovers the server metadata and a fresh signed identity challenge verifies it; local loopback HTTP requires an explicit development setting. TOTP and recovery codes were removed in 0.2.0.

Text clipboard directions are separately requested and approved, with both local OS directions off until each endpoint explicitly chooses them. One-shot actions reuse the Core clipboard route and exact request/connection/Core binding; Android access requires the resumed, focused, unlocked application. There are no system clipboard listeners or automatic text polling. Plain UTF-8 text is bounded to 64 KiB and clipboard contents never enter UI state, JSON status or logs. These source changes still require fresh Rust/JNI, JVM and API 30–36 device verification; see [the Android clipboard contract](../../docs/refactor/ANDROID-CLIPBOARD.md).

Build prerequisites: JDK 17, Android SDK platform/build tools 36, NDK 27.2.12479018, Rust targets `aarch64-linux-android` and `x86_64-linux-android`, and `cargo-ndk 3.5.4`. From the repository root, build with `bash apps/android/gradlew -p apps/android :app:assembleDebug`; Windows uses `apps/android/gradlew.bat`. On Windows, run the offline JVM suite with `powershell -ExecutionPolicy Bypass -File scripts/test-android-unit.ps1`; it creates and removes an unused temporary drive mapping so the JUnit worker can load test classes from the supported Chinese workspace path. The unit-test entry excludes Rust/Cargo tasks and leaves `CARGO_TARGET_DIR` untouched. Gradle resolves the Rust shared-object outputs under `CARGO_TARGET_DIR` when set, or the workspace `target` directory otherwise. Rust and Android dependencies are locked and checksum-verified. The Android Gradle path check is disabled because the supported Windows workspace lives under a Chinese path; builds are verified there directly. Release signing is intentionally configured through external CI secrets and is not supplied in this repository.
