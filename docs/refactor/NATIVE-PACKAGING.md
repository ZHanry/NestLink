# v15 native package lifecycle

The native payload/package recipes are separate from the 14.x distribution. Windows installs per user below `%LOCALAPPDATA%\Programs\NestLink-v15`; Ubuntu installs `nestlink-v15-desktop` and `nestlink-v15-server`, below `/usr/lib/nestlink-v15/{desktop,server}`. Neither recipe reads, stops, imports or removes the legacy product or `/opt/home-tunnel-server/v14.0.1`.

This is implementation and a preparation workflow. No release certificate is configured, and these recipes have not passed real installation, upgrade, rollback or removal acceptance. The release must stay blocked until the final signed bytes pass those checks.

## Ownership and graceful maintenance

`nestlink-daemon maintenance --state-dir <absolute-v15-directory> --control-dir <state-dir>/maintenance-<UUID>` takes exclusive startup admission before connecting. It authenticates through the existing purpose-separated mutual TLS IPC key, captures the current runtime and generation, and sends `Exit` once on that same ordered connection. An ambiguous or failed reply is never replayed on a replacement runtime. The owner waits for the actual daemon singleton lease and every registered desktop/native-chooser lifetime lease to release; absence of an endpoint is not proof of completion.

Only then does it create the private `ready.json`. With `--installation-dir`, this record includes a boolean `installation_recovery`, captured from an existing valid installation journal while exclusive installation admission is held. Ordinary user-only maintenance omits that field. The Windows helper requires the typed flag, the installation journal and the original live controller PID/creation time; failed, released, abandoned or already consumed controls cannot authorize Commit. Its caller retains the owner through package changes, then creates a private, create-new `release.json` containing `{"schema_version":1,"control_id":"<the-same-UUID>","action":"release"}`. The owner explicitly releases and creates `released.json`. Quiescence and holding have separate bounded deadlines, at most 120 and 1800 seconds. The `shutdown` subcommand performs the same graceful exit/quiescence without holding admission after success.

Failure, timeout or controller crash preserves `maintenance-incomplete.json`; startup remains refused after the OS lock is released. A new explicit maintenance owner can reacquire the locks, inspect/repair the package transaction and finish release. Never remove lock files or the journal to make an installation appear healthy. `--installation-dir` also holds the per-user Windows install root, so the packaged default application cannot restart during the change. Ubuntu's root owner holds that same install admission before discovering users, then runs each user maintenance controller with `runuser`; user daemons do not run as root.

A failed or cancelled Windows transaction creates the same authenticated control message with `"action":"abandon"`. The native owner drops the user and installation OS owners, retains both durable incomplete journals and records `abandoned.json`. This permits a new recovery owner to acquire the locks without waiting for the old hold deadline while startup remains blocked. Only completed Commit or completed uninstall sends `release`; deinitialization after failure never clears the fences. The original control and temporary-controller evidence are retained after abandon.

The installed namespace has stable `installation-v15.json`, `installation-admission.lock` and a transaction journal. Desktop/daemon startup shares install admission until its real state lifetime owner is established. New users/custom states cannot race a machine-wide DEB change. Existing desktop windows, including hidden tray windows, observe per-user maintenance and close their workers. Native chooser children carry the exact parent's state directory and their own lifetime lease. No path uses process-name killing or a system-permission proxy.

## Fixed manifests, independent signatures and builds

Use `config/native-payload.template.json` for the exact final signed executable bytes. Fill the final commit, real state compatibility identifiers and Windows code-signing certificate SHA-256. `null` is deliberately unusable. `freeze` computes byte lengths/hashes, requires a clean exact HEAD and the final Cargo workspace version, and refuses to overwrite its output:

```text
python scripts/refactor-native-packaging.py freeze --plan artifacts/native-payload-plan.json --bundle artifacts/native-payloads --output artifacts/native-payloads/payload.json
```

Sign the exact `payload.json` as detached binary CMS DER using the separately controlled update-signing identity, producing `payload.p7s`. Supply one public PEM certificate plus its SHA-256 of DER, enrolled independently of the downloaded bundle. No build script creates a key/certificate or accepts a bundle-provided identity as its trust anchor. The OpenSSL verifier uses `-nointern` with only that pinned public certificate. `-noverify` skips the public PKI chain because this independent pin is the update trust anchor; cryptographic signature verification remains mandatory. Windows also checks Authenticode system trust, exact code-signing certificate, EKU and timestamp on both native PEs, final setup and the compiler's signed uninstaller. The update pin must differ from Authenticode.

Build each Linux architecture/role from that one signed payload statement:

```text
python scripts/refactor-native-packaging.py build-deb --bundle artifacts/native-payloads --manifest artifacts/native-payloads/payload.json --signature artifacts/native-payloads/payload.p7s --certificate <public-update.crt> --certificate-sha256 <independently-enrolled-DER-SHA256> --architecture x86_64 --role desktop --maintainer "<actual-name> <actual-email>" --output artifacts/native-packages/NestLink-linux-x64.deb
```

Repeat with `aarch64`, and with `--role server`. The package architecture is checked from the ELF header, not inferred from its filename. First create the approved output directory; the builder cleans only its own temporary staging directory. The Linux desktop and server tools have separate paths, so both DEBs can coexist.

On Windows, use `build-windows` with the same signed payload options, `--iscc <Inno-6-compiler>` and `--inno-sign-command <your-configured-timestamped-Authenticode-command>`. Inno must sign setup and uninstaller. The configured command is build configuration; it is never read from a downloaded manifest, printed, synthesized with a development certificate or checked into source with a secret.

After signing and packaging, use `config/native-packages.template.json` and `freeze` again to create a **different** `native-packages` statement with the final installer/DEB hashes. Bind every package to the exact signed payload manifest SHA-256, source revision, release sequence and state compatibility. Sign this second statement with the independent update identity. This avoids a package/embedded-manifest hash cycle. Final installation acceptance and promotion use those already fixed package bytes. Repacking or signing changes bytes and invalidates the corresponding acceptance.

## Windows behavior

The Inno setup embeds the fixed signed payload and reviewed PowerShell owner. Before writing package files it verifies payload CMS/Authenticode, copies the already verified maintenance PE into one fresh private temporary folder, and waits for native quiescence. The maintenance process retains the private state and installation gates while Inno runs. Other custom v15 instances still owning installed executables are reported and left running until explicitly stopped.

Each version goes under `versions/<version>-r<sequence>` with `onlyifdoesntexist`; a failed candidate can be retried only if its existing bytes verify against the exact signed statement. Commit atomically records the accepted version, previous version and monotonically increasing maximum sequence, then updates this user's `NestLink v15` shortcut. A shortcut failure restores the old receipt. A normal setup cannot downgrade or rotate the independent update key implicitly. `Manage-NestLink.ps1 -Action Rollback` enters maintenance, verifies the exact previous retained signed payload, requires identical declared state compatibility and switches only the accepted binary/shortcut record. The maximum accepted sequence never decreases.

Recovery after Commit but before release additionally requires the native held-gate recovery flag and the unchanged active installation UUID. Incoming, current and maximum accepted records must match exactly, including directory, version, sequence, source revision, manifest hash, both certificate pins and state compatibility, and use the maximum accepted sequence. This exact retry preserves the original previous record. It does not permit ordinary active replay, lower sequences or replacing the accepted bytes. Receipt/instance discovery and rollback selection are repeated after acquiring the native gate so that a concurrent completed transaction cannot supply stale acceptance state.

Uninstall enters the same native maintenance owner and removes only Inno's registered files/shortcut. It retains user state, private identities, durable quotas, receipts and backups. Temporary controller files are removed only after confirmed release and actual controller exit, with exact nonrecursive paths. A maintenance failure retains its control/journal evidence for recovery. Explicit exit remains respected: setup offers an optional launch, and rollback does not restart the UI automatically.

## Ubuntu behavior

Install only through the verified owner (the selected package may be cached independently of other platforms' files):

```text
sudo python3 packaging/linux/lifecycle.py install --role desktop --bundle <final-package-directory> --manifest <signed-native-packages.json> --signature <signed-native-packages.p7s> --certificate <public-update.crt> --certificate-sha256 <independently-enrolled-DER-SHA256> --artifact-id linux-x86_64-desktop
sudo python3 /usr/lib/nestlink-v15-tools/desktop/lifecycle.py rollback --role desktop
sudo python3 /usr/lib/nestlink-v15-tools/desktop/lifecycle.py uninstall --role desktop
```

The root owner takes global admission before discovery, copies the selected package plus statements/certificate to a private root cache, reverifies those copies and executes **only the cached package**. A mutable user's download path is never passed to apt/dpkg. It checks DEB name/version/host architecture, the installed independently signed inner payload statement, same source/sequence and exact installed executable hashes before activation. Maintainer hooks require the matching root transaction ID, so direct `dpkg -i/-r` does not silently bypass lifecycle coordination. Distribution dependencies still use Ubuntu's normal signed apt repositories.

The user daemon unit is disabled by default and uses `Restart=no`, `KillSignal=SIGINT`, and no forced SIGKILL. Enable it only as an explicit login-autostart choice; opening the desktop otherwise starts its sibling normally. The server uses the dedicated unprivileged `nestlink-v15` account and `nestlink-v15-control.service`, preserves its private state parent, and does not initialize an account/deployment or open a firewall automatically. After installation, explicitly initialize a NEW `/var/lib/nestlink-v15/control` with the intended management origin, bootstrap using the existing private password-file command, then enable the service. The existing Caddy, web-assets, node/TURN and firewall deployment templates need their own deployment acceptance; this package does not adopt an existing Caddy service or edit its configuration.

Successful upgrades keep the exact previous package in the root-private rollback cache and preserve the maximum accepted sequence. Explicit rollback can use only that previous accepted cache entry with matching state compatibility. A failed upgrade attempts to reinstall and reverify the old exact package, while retaining an incomplete-installation journal until explicit `--recover-incomplete` repair finishes. It never silently copies an old database over new authorization state. `remove`/`purge` hooks keep user state, update trust, receipts, backups and rollback cache; no legacy package or global apt dependency cleanup is invoked.
