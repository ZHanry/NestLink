# 区分接收端解码压力与网络拥塞

状态：源码修复，等待 GitHub 托管 Actions 的原媒体、弱网和严格检查。

真实内核弱网 sourceadef482/run41370354628 保留了生产者与实际接收报告。
在尚未从 20Mbps 降至 5Mbps 的阶段，动态伪随机图像给 CPU codec 带来
约 34–43ms 编码成本，接收端报告 Congested；码率随后降至 800kbps，
触发未改动的阶跃前提失败。这不是通过弱网验收的证据。

原接收报告已经分别包含最后完成序号、实际解码数和最大解码耗时，
但 tracker 把解码成本超限也归为网络 Congested，生产 VideoQuality
因而削减码率。比较放宽报告门槛、减少实验负载和区分既有事实，选择
第三种。所有报告校验、500ms 观察、原 1.25 帧周期成本门槛、正常报告
延迟、缺失/过期处理和 500ms 调整节奏保持不变。

新增本机 DecoderLimited 条件：实际解码成本/进度不足先按原 codec
受限策略降低生产 cadence；它不能证明可用网络带宽下降。没有解码
受限事实时，原序号滞后仍报告 Congested，原排队超 40ms 也仍削减
码率。两种瓶颈可依次被观测和处理，既不扩大已批准 fps/码率，也不
依靠未认证或过期报告升级。复用现有报告与 VideoQuality，不新增线
协议、拥塞控制器、传输队列或全局资源 owner。

修复覆盖使用原报告 tracker/VideoQuality 的固定 VP8 与本机 Core
生产策略；具体硬件 owner 仍须各自真实验证。新回归分别要求高解码
成本降低 cadence 而不虚构网络码率、真实滞后继续减码率，原缺失反馈
和恢复滞回测试保留。实际 2 秒阶跃、输入 p95+10ms 和持续呈现门槛
保持；仍须真实 tc 重跑，不以新单元测试宣称完整 W31 或 AC53 通过。
