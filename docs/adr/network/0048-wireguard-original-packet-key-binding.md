# ADR 0048: Independently bind a standard WireGuard client to its original packet business

Date: 2026-10-31. Status: first production key-binding slice implemented; Actions compilation and qualification pending. W24 remains in progress.

## Decision and alternatives

Use the Linux kernel WireGuard implementation and official distribution `wireguard-tools` as the first portal provider. WireGuard owns X25519 handshakes, encrypted transport, peer authentication and exact per-peer AllowedIPs. Reuse the original NestLink signed membership, separately approved subnet mapping, NetworkAccess/Connectivity/Path graph, durable one-use source claim and noncloneable online packet budget. Add an independently signed client-key binding and the small privileged owner that connects these authorities. No new Rust crypto or WireGuard protocol implementation is introduced.

A portal-wide peer or a public-key/IP lookup without the original business was rejected: possession of one client's key must not inherit another client's ACL, destination, quota or portal permissions. BoringTun 0.7.1 remains a reviewed fallback candidate for a future platform that needs userspace WireGuard; selecting it now would add an unnecessary packet/tunnel stack and a second implementation to qualify. Existing TUN, nftables and journaled privileged ownership are reused where suitable instead of adding a second general firewall or network stack.

## Frozen version-one authority

`wireguard::WireGuardClientBindingClaims` is canonical bounded JSON, signed by the original provisioned space Ed25519 authority under `NestLink/wireguard/v1/original-packet-client-binding\0`. Its digest has a separate purpose. The WireGuard X25519 public key is independent from the portal installation's Ed25519 key. The claims bind one stable client ID and revision, owning account and installation, one exact private IPv4 /32, current registered portal node key and boot incarnation, original NetworkAccess grant ID and digest, finite expiry and the complete original byte promise. The signature never authorizes a replacement NetworkAccess, source prefix, service lease or all of a portal's permissions.

The owning source account must explicitly create this wrapper after the destination account approved the original packet graph. Ordinary space membership is sufficient only for entering this management operation; the original source account, exact installation/membership key and separately approved same-address /32 source mapping are still required. The manager's role cannot substitute for another account's ownership. The /32 may not be borrowed from an installation's managed host address. The manager independently approves the RouteExport/mapping and the installation's owner independently binds the installation to that exact mapping. An existing accepted node lease independently proves the portal's node key and current boot. Version one deliberately rejects a broad source subnet and translated client source prefix.

Registered routes are `POST /network/spaces/{space}/wireguard-client-bindings` (201), `GET /network/spaces/{space}/wireguard-client-bindings/{binding}` (200), and `DELETE` on the same binding (200 current policy). Requests carry expected policy/client revisions and expected portal incarnation. GET returns the exact original signed binding, original packet credentials, fresh mapping/node readback and current policy. Route DTOs and the xtask schema registry are included in this slice. Generated OpenAPI must be imported from Actions, never generated locally.

Schema 47 retains each client's immutable total byte ceiling and cumulative committed original packet promises across key rotation and database reopening. Issuing a binding commits the complete independently issued NetworkAccess byte limit, even if its owner crashes or never starts. The same original NetworkAccess cannot back another binding. Rotation requires a fresh destination-approved original graph, fresh key and noncolliding /32, increments the client revision and closes all old binding/business graph IDs atomically. The old public key and address remain reserved until the old binding's finite deadline because a failed original helper may still own physical state. Revocation, observed invalidity and expiry close the original access, connectivity and path as well as the wrapper; current policy snapshots propagate that closure. A partial transaction does not debit a client, reserve a name or revoke its prior binding.

This conservative quota allocation deliberately retains uncertain promises and does not refund a failed or rotated grant. It prevents restart/rotation from minting new credit. A future quota increase or verified refund needs an independent reviewed quota operation; reissuing this wrapper cannot change the original ceiling. Bounded history and simultaneous namespace limits fail explicitly.

`OnlineWireGuardClient` requires separate explicit approval of the binding digest and original business digest, verifies the provisioned authority and local installation/account, consumes the original OnlinePacketAccess one-use start and retains that same packet owner. It cannot be cloned or deserialized into new credit. Every packet still passes the original complete-IP parser, source/destination ownership, exact L3/L4 ACL, direction and cumulative byte ceiling. Binding expiry, original business lifetime, the latest verified portal lease and a five-second online-observation bound all constrain admission. Successful refresh may observe a renewed lease for the same portal boot, but never moves the original binding deadline or replenishes bytes. Any refresh error is terminal for that original owner; recovery needs new explicit original business approval.

## Kernel owner and product work still required

The production Linux owner must create one exact, explicitly approved WireGuard interface/peer resource for the bound client, put only the client's /32 in its kernel AllowedIPs, and transfer packets through the same original noncloneable packet owner and authenticated packet carrier. Merely routing WG packets around that owner would bypass the business meter and is forbidden. The return path must admit the original reverse flow before writing to WireGuard. Do not replay queued packets after owner replacement.

The privileged helper must authenticate the original live ordinary process, UID, local consent, exact binding/business/mapping digests, existing selected interfaces and fixed underlay endpoint. Its root-private durable journal and exact owned interface alias/index/name must precede any resource creation. Use typed argument vectors for `ip`/`wg` and file descriptors or private stdin for secrets; never log or serialize a portal private key into a public plan. Bound routes, forwarding and nftables must be restricted to the exact owned interface and source /32. A helper crash must leave a durable deny fence or destroy the exact owned interface. Expiry/revoke/logout, partial install, upgrade, uninstall and changed/foreign-resource cases require physical cleanup readback. Never flush unrelated routes, shared conntrack, firewall state or another VPN.

The CLI, protected configuration export and QR generation, Linux privileged WG owner, exact provider package/license/runtime evidence and actual standard WireGuard experiments remain required next slices. The client config must contain one independent private key, explicit endpoint/server key, one address and only approved destination prefixes; secrets require explicit protected export and never ordinary logs/diagnostic bundles. UI must identify this client and gateway path and expose rotation/revocation/error/cleanup state.

Hosted tests in the first slice exercise purpose isolation, canonical encoding and altered signatures; real HTTP/SQLite source-account/installation/address/boot checks; original packet source/port refusal, one-use start and retained spent bytes; all-graph revocation; key rotation with retained names and immutable cumulative quota across reopening; portal restart; observed finite expiry and rollback refusal. They do not claim a real WireGuard handshake or Android/iOS acceptance. Those require a dedicated hosted kernel workflow and the separately recorded actual Android and iOS standard-client devices.

All compilation, formatting, lint, generated API, tests, native tooling installation and kernel experiments run in GitHub-hosted Actions under R02. This slice was reviewed as source locally and does not mark W24 complete or authorize its release independently.
