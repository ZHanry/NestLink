# Linux TUN owner UID uses a scalar ioctl argument

Status: accepted for source implementation; actual ordinary-UID/native rerun required.

The hosted native lab on source `297211e0dd501ffe688c155ae054604732744d35`
created a fresh ephemeral TUN with the expected marker and empty configuration,
but actual kernel readback reported `uid_match=false`. The existing strict
identity gate rejected it before persistence and ordinary descriptor adoption.

The selected maintained `tun-rs` 2.8.16 owns device creation, packet I/O,
descriptor lifecycle and persistence. Its Linux `user()` currently invokes
`tunsetowner(fd, &value)` generated by `ioctl_write_ptr!`. Linux instead consumes
the scalar `arg` with `make_kuid(current_user_ns(), arg)` in `case TUNSETOWNER`.
Passing the address of a UID therefore does not set that UID.

Reviewed sources:

- [Linux v6.18 TUN implementation](https://github.com/torvalds/linux/blob/v6.18/drivers/net/tun.c), `__tun_chr_ioctl`, `case TUNSETOWNER`.
- [Linux v6.18 TUN ioctl declarations](https://github.com/torvalds/linux/blob/v6.18/include/uapi/linux/if_tun.h), `_IOW('T', 204, int)`.
- [tun-rs 2.8.16 Linux user adapter](https://docs.rs/crate/tun-rs/2.8.16/source/src/platform/linux/device.rs), `user()`; and `src/platform/linux/sys.rs`, `tunsetowner`.
- [rustix 1.1.2 ioctl patterns](https://github.com/bytecodealliance/rustix/blob/v1.1.2/src/ioctl/patterns.rs), `IntegerSetter`.

Using the selected provider unchanged fails this required ownership boundary.
Creating or attaching a device with a separate `ip tuntap` process would lose
the already retained original descriptor and introduce an avoidable attachment
race. Replacing the entire driver wrapper would repeat reliable existing code.

The narrow correction reuses the existing `rustix` dependency's `IntegerSetter`
with its portable ioctl opcode construction inside `platform-security`. Its
single unsafe call is isolated there; daemon code remains unsafe-free. It acts
only on the still-open creating descriptor and passes the signed plan's exact
ordinary UID. The actual kernel UID remains mandatory in ephemeral identity
readback, durable journal identity, configured state and ordinary admission.
No ownership check or persistence ordering is relaxed. No driver, packet ring,
transport, authorization or general ioctl engine is introduced.

The existing hosted native ordinary-UID/root-helper test must rerun on this
exact source to prove descriptor adoption, complete dual-stack packets and
normal/crash cleanup. Source review alone is not runtime evidence.
