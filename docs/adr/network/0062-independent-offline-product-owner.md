# Independent finite offline remote product owner

The SDK already authenticates a separately signed, online-consumed, original-process offline authority over explicit direct QUIC or TLS. Its original `ChannelRuntime` uses the same business queues and delivery checks as remote control. AppCore previously had no caller that could publish that runtime to its native data routes.

Extending the online native actor would reuse its management polling and recovery machinery, but those paths require a current online permit and authenticated management generation. An offline owner deliberately cannot export such a permit. Treating its frozen metadata permit as renewable authority would cross the independent lifetime and quota boundary.

The chosen adapter is `NativeOfflineRemote` and its one `NativeOfflineSession`. It accepts only the SDK's already consumed in-memory `OfflineRemoteOwner`, retains that original owner across permitted carrier attempts, and allows one listener or data lifecycle at a time. QUIC and TLS remain explicit signed direct transport choices. Cancellation or explicit stop ends the original authority. Online synchronization retires offline deliveries before reading current management state; ordinary online continuation still needs fresh authorization.

Read-only SDK scope projection supplies the exact original request/generation and the offline operations. AppCore derives route permissions from those operations, including narrower permissions than the frozen online metadata. Existing native display/video, input, audio, clipboard and file routes perform their existing delivery and local platform-consent checks. Their queues, codecs, filesystem access, input release and cleanup remain with the mature original owners. `Shared` and the native host video constructor are reused by both product lifecycles.

The independent data `Snapshot` stays management-disconnected and carries no fabricated server, principal or online login. `native_offline` explicitly projects finite budget, operations, carrier and cleanup facts. The exact native stop action is the only accepted product action and completes after actual cleanup. Unsupported online actions fail. Platform cleanup that still has an original reaper retains the lifecycle permit; bounded shutdown reports pending while that join remains outstanding.

The same-source hosted integration cases create real two-account HTTP approval and consumption receipts, stop management, wait past the unchanged online permit deadline, and run explicit QUIC and TLS AppCore sessions. They cover actual VP8 encode/decode/pixel delivery, an approved handle-relative 262144-byte OS file read into a private no-clobber download, narrower Input/FileWrite denial, original finite-byte charging, stop/process invalidation, stale data rejection, capture reset and physical host socket rebinding. A real silent peer consumes an attempt before the successful explicit retry; the same bundle and reduced lifetime remain unchanged. These cases are implementation work until their exact-source Actions executions pass.

The resident `offline-remote` CLI restores the existing protected login under the original installation singleton, retains the original process nonce and consumed authority, and exposes the existing authenticated local IPC only after actual business proof. It reuses the private-service resident's login/identity/maintenance guard and bounded JSON interaction. Review, approve, one-use activate and explicit direct start remain separate steps. Platform capture/audio/clipboard/input and approved files use the existing daemon adapters. Ordinary transport loss joins the old lifecycle and platform workers before permitting another explicit start under the original budget; cancellation, logout, maintenance, explicit stop and online synchronization terminate authority. Setup errors wait for the QUIC physical release receipt; cancelled setup retains its original endpoint in a reaper and makes no completed-cleanup claim.

The desktop presents an independent offline workspace with finite scope and budget while management authentication stays disconnected. Its exact session/generation selects the existing display, video, input, clipboard and files APIs. Opening the viewport does not inspect an online request. Closing it submits only the exact local stop and waits for both native cleanup and the original offline authority's terminal receipt; it does not submit an online revocation or claim that a central revoke arrived. The resident keeps that completed IPC snapshot available until explicit process exit. Shared original file quota/recovery stores survive permitted carrier attempts, while each new session gets separate data handlers and fresh local consent.

The original product owner also allocates a strictly increasing local IPC generation for every attached lifecycle, including a rebuilt carrier whose signed request/connection metadata remain frozen. Queued data from a previous local generation cannot cross into a rebuilt lifecycle. The explicit resident `rebuild` command fences current data and retires its carrier with `NetworkChanged`; after actual cleanup, another explicit `start` spends the same original finite reservation. This path neither stops nor renews that authority. The desktop's separate “End offline authority” action remains terminal. Integration assertions require two real proved lifecycles, old-generation rejection, no old-pixel replay, exact second OS file delivery and cumulative charging without a new bundle.

The resident's first media path accepts ordinary VP8/H264 scope. Advanced media scope requires the original live media execution binding and is explicitly rejected until that binding is connected. No real physical dual-device, GPU, NAT or mobile qualification is implied by the resident implementation.
