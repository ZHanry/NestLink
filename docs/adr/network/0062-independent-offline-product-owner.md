# Independent finite offline remote product owner

The SDK already authenticates a separately signed, online-consumed, original-process offline authority over explicit direct QUIC or TLS. Its original `ChannelRuntime` uses the same business queues and delivery checks as remote control. AppCore previously had no caller that could publish that runtime to its native data routes.

Extending the online native actor would reuse its management polling and recovery machinery, but those paths require a current online permit and authenticated management generation. An offline owner deliberately cannot export such a permit. Treating its frozen metadata permit as renewable authority would cross the independent lifetime and quota boundary.

The chosen adapter is `NativeOfflineRemote` and its one `NativeOfflineSession`. It accepts only the SDK's already consumed in-memory `OfflineRemoteOwner`, retains that original owner across permitted carrier attempts, and allows one listener or data lifecycle at a time. QUIC and TLS remain explicit signed direct transport choices. Cancellation or explicit stop ends the original authority. Online synchronization retires offline deliveries before reading current management state; ordinary online continuation still needs fresh authorization.

Read-only SDK scope projection supplies the exact original request/generation and the offline operations. AppCore derives route permissions from those operations, including narrower permissions than the frozen online metadata. Existing native display/video, input, audio, clipboard and file routes perform their existing delivery and local platform-consent checks. Their queues, codecs, filesystem access, input release and cleanup remain with the mature original owners. `Shared` and the native host video constructor are reused by both product lifecycles.

The independent data `Snapshot` stays management-disconnected and carries no fabricated server, principal or online login. `native_offline` explicitly projects finite budget, operations, carrier and cleanup facts. The exact native stop action is the only accepted product action and completes after actual cleanup. Unsupported online actions fail. Platform cleanup that still has an original reaper retains the lifecycle permit; bounded shutdown reports pending while that join remains outstanding.

The same-source hosted integration cases create real two-account HTTP approval and consumption receipts, stop management, wait past the unchanged online permit deadline, and run explicit QUIC and TLS AppCore sessions. They cover actual VP8 encode/decode/pixel delivery, an approved handle-relative 262144-byte OS file read into a private no-clobber download, narrower Input/FileWrite denial, original finite-byte charging, stop/process invalidation, stale data rejection, capture reset and physical host socket rebinding. These new cases are implementation work until their exact-source Actions executions pass. Desktop/resident CLI attachment is a separate continuation and is not claimed by this initial adapter commit.
