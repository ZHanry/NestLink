# 给 Codex 的执行指令

版本 1.1：全局硬约束 R01 成熟组件优先复用；R02 所有编译及自动化验证在 GitHub Actions 执行。

使用方式：在 Codex 打开 ZHanry/NestLink 仓库，将本套文件放在 docs/network-rewrite/，把下面“开始执行”至文件末尾的内容作为任务发给 Codex。若目录中已有同名文件，先比较并保留已有进度，不能直接覆盖。首次执行记录当前真实 SHA；本方案研究基线不要求强制回退仓库。

## 开始执行

你正在开发 ZHanry/NestLink。请执行 docs/network-rewrite/NESTLINK-REWRITE-SPEC.md 和 docs/network-rewrite/NESTLINK-TASKS.json，完成其中全部功能，而不是仅评审、重复规划或搭建骨架。

目标是在现有 NestLink 上，深入研究 EasyTier 后，自主设计统一网络内核，并接通全部产品功能。最终运行不依赖 EasyTier 可执行文件、核心库、FFI 或源码 Fork。自主代码聚焦 NestLink 特有的空间、权限、连接编排、调度策略、业务生命周期和适配；全部通用能力优先复用现有实现及成熟组件。不能把“自主”解释为底层代码全部重写。

### 零、两条全局硬约束

**R01：成熟组件优先，禁止重复造轮子。** 先复用仓库已有可靠实现，再选择满足需求的成熟组件，最后只为确有必要的产品差异编写薄适配或最小新实现。此规则覆盖协议、网络栈、TUN驱动、代理/DNS/网关、媒体、数据库、配置、日志、指标、安装更新、UI和测试工具，不限于密码学。

W01 建立 components.json，记录候选、来源、维护状态、平台/版本/许可证、选择及适配边界，W02 冻结首批依赖。现成组件无法满足必要需求时，在 ADR 写出实际缺口、不采用理由和最小自研范围；不能以“自主”“统一代码风格”为理由从零重写成熟通用组件。该决策记录不新增逐项审批。

**R02：所有编译、自动化检查、测试、打包和制品生成都通过 GitHub Actions 执行。** 覆盖依赖/工具链安装、代码生成、cargo fmt/check/clippy/build/test/run/bench、fuzz、前端依赖及构建、WASM、原生依赖、网络原型、Docker/OCI、安装包、签名和SBOM。规则从第一次原型开始生效，不限正式版；禁止本地“快速跑一下”，也禁止依赖安装或脚本隐式触发本地编译。

Codex 工作区可以读写源码、搜索、人工审阅、操作 Git、读取 Actions 日志、下载并校验制品及维护文档；不能启动项目开发服务器、编译器、formatter、lint 或本地测试。格式修改由 Actions 输出补丁后在工作区审阅应用。构建使用 GitHub 托管 runner，不能把用户电脑或部署服务器注册成 self-hosted runner 绕过约束。

Windows/GPU、手机、真实公网/NAT和长稳验收，可以在真实设备运行 Actions 已生成并核验的应用、验收工具和脚本；现场不从源码构建、不安装会触发编译的开发依赖。编译来源和现场执行来源分别记录。缺 runner、权限或额度时保留待验证并继续其他源码工作，不能改成本地编译。

### 一、读取与范围

1. 先读当前有效 AGENTS.md、工作树状态、产品范围、兼容矩阵、构建与验收文档，再完整阅读本套开发规格和任务清单。保护用户未提交的工作，在适当分支或隔离 worktree 开发；不重置或覆盖无关修改。
2. 研究基线是 NestLink 82f1c8dfb31bdf0872ea7430b5608e205c1cbb08。执行时核对最新代码与该基线的差异；实际新增修复应继承，过时路径应更新并登记，不能盲目按旧目录新建重复模块。
3. 26 项功能、41 个工作包和 70 组验收全部纳入最终范围。阶段表示依赖顺序；“可选 TUN”“可选离线”等表示用户可选择启用，不能用来删减开发范围。
4. Windows/Web/Linux 后端是主要交付平台；Linux 增加无图形组网和网关角色；Android 与 iOS 均通过标准 WireGuard 客户端实测。本任务不要求恢复 Android/iOS/macOS 原生远控客户端。
5. 本次新需求包含空间、TUN、子网、WireGuard、有限离线和多入口 HA。将范围变化写入版本化需求，不悄悄修改历史验收结论。若历史文档范围与本次明确要求冲突，保留历史记录并明确新旧适用关系；真实权限和发布门禁仍按当前有效指令执行。

### 三、实现顺序与连续执行

从 W00/W01 开始，完成基线与机制研究；冻结 W02 协议/授权契约，随后按 NESTLINK-TASKS.json 的 depends_on 选择就绪任务。阶段名用于组织，DAG 决定实际依赖。研究、基线、契约等按各自明确产物和证据结项，不强行要求研究任务先新增生产入口。实现迭代必须接通真实路径，并继续推进后续就绪工作，不在提交接口或研究文档后自动结束项目。

W00 先核对现有 Actions 入口，W03 提前建立新增模块的构建、自动检查、测试、原型和实验工作流；后续实现同步扩展，不能等到 W34 才配置 CI。第一批可运行结果要包含：真实 legacy 行为经新接口运行、双方身份与用途授权、真实 QUIC/TLS/WSS 承载、不透明端到端数据报、故障注入和可复核日志。全部由 Actions 构建并验证。然后实现双方穿透、主备/多跳和会话迁移，再接入远控与服务，继续交付空间、目录、名称、代理、TUN、子网、WireGuard、Web 网关、HA、离线、游戏、诊断、媒体、安装和全部验收。

按协议与网络、网关与服务、产品 UI、验证工具分工并行；共享线协议、签名对象和系统资源 owner 由单一负责人维护。接口未冻结时不要让多个代理各造一套生产调度器。独立审阅实际调用链、权限、失败分支和资源回收，不只检查测试数量。

### 四、不可省略的工程约束

- 网络成员资格、连接路径、业务、转发/子网和原始 IP 访问权限分别校验。加入空间不自动获得远控输入、文件写入或任意本机端口访问权。
- 不兼容 PathGrant 的业务分开建立传输组。direct_only 业务不能因为共享 QUIC 连接而一起转入 relay。
- 双向 NAT 检查和真实业务使用同一 UDP socket 或成熟库支持的同一数据报接口；验证实际 MTU 与封装预算。W07/W09 的可行性必须以真实承载证明。
- 迁移正常优化和旧路径彻底断开均可完成认证协商；明确同时提议、确认丢失和超时。区分业务代次与路径代次：合法旧路径可有限排空，撤销和终态优先。
- 先证明当前 Quinn/虚拟 UDP 能安全保持连接，才能声明相应连续性；不能保持时安全恢复应用会话。不重放旧输入、剪贴板写入、过期音频或任意 TCP 业务请求。
- 中继看不到内层业务明文；外层路由头和转发许可也要认证。端点处理业务 QoS，relay 按授权传输组调度，不能假装可以解析加密包内的媒体帧。
- 默认远控及单服务访问不依赖 TUN。TUN 注入 OS/LAN 前检查认证 Peer、获准源地址/前缀及 L3/L4 ACL；分片和 IPv6 扩展头不能绕过检查。
- private/public/both 独立准入但共享原有累计总预算。公网 HA 必须包含真正固定入口和双 edge 实测，覆盖 HTTP/HTTPS/TCP/UDP 及所有入口撤销；没有复制状态就不承诺旧连接不中断。
- 离线仅开放预授权受信设备间的直连远控和私有服务，使用完整独立离线授权链、有限期限和预留额度，不静默延长中继/网关在线租约。中心失联时不能声称立即收到中心撤销。
- 保留浏览器 WebRTC/ICE/TURN。普通 Web 页面不具备通用 TUN 或任意 TCP/UDP 能力；私有 Web 网关隔离 origin 并限制目标。
- Windows/Linux 路由、DNS、网卡和映射有归属，崩溃、升级、退出和卸载均清理或恢复本产品资源，不破坏其他 VPN。
- 媒体是独立工作包。原报告要求的 GPU、H.264、高阶格式、弱网和文件并发必须真实接线，不把网络改善等同于媒体性能达标。

### 五、验证、进度与外部资源

按每个工作包的正向、反例、证据层级和完整用例实施验证，所有任务与代理继承 R01/R02。每轮编辑后提交并推送已授权开发分支，通过 GitHub Actions 执行必要的格式/lint、编译、测试、原型、bench/fuzz和打包，再读取对应 SHA 的日志、修复并继续。L0/L1及可自动化L2在Actions执行，真实设备步骤只运行核验后的制品。不能修改断言、放宽门槛、跳过失败或使用旧制品通过记录来结项。

证据分别记录 build_provenance（Actions workflow/job/run/attempt、runner、源码SHA、依赖锁、制品摘要）与 execution_provenance（Actions实验或真实设备运行环境及日志）。不能把“CI构建了验收程序”写成“CI已经执行了真机验收”。

逐项更新 NESTLINK-TASKS.json。任务状态区分 not_started、in_progress、implemented_unverified、verified_lab、verified_target、blocked_external、released。外部阻塞同时保留实现状态、验证状态及具体原因，不能把未实现部分藏进 blocked_external。70 组用例分别保存状态和证据；整组全部适用子场景通过才记 passed。

在 docs/network-rewrite/progress.json 记录当前分支/SHA、正在执行的 W 编号、已满足的接口依赖、未验证假设、外部前置、下一步和证据索引。每次上下文或会话切换前更新检查点；恢复时从真实代码、任务和证据继续，不重头生成计划。

缺 Windows/GPU、Android/iOS、真实公网/NAT、域名、签名或其他资源时，先完成独立可做的实现、候选制品、验收脚本和运行手册。只有确实依赖这些资源的现场用例保持待验证，其他就绪任务继续执行。前置只欠现场验证时，不阻塞不依赖其结论的下游开发；W07/W09/W14 等关键原型的未证实假设不能当作已成立。

需要用户操作时，集中提供已经准备好的具体制品、最短操作步骤、所需资源和对应验收编号，说明为何当前环境无法完成。不要反复逐阶段询问是否继续。没有真实设备证据就不能编造通过；也不能因为暂缺一台手机而将整个项目停在设计阶段。

本指令授权在当前仓库开展上述开发、修复和必要验证。实际生产部署、公开发布、破坏性迁移、向他人发送邀请和修改权限，仍依用户已给出的实际授权和仓库门禁执行；不得仅凭计划文件推定已授权这些外部动作。

### 六、完成判定与汇报

每个功能都要具备生产调用入口、实际业务数据、权限校验、用户可操作 UI/CLI、错误处理、撤销/清理和适用证据。trait、占位页面、配置字段、mock、单次 ping、UDP echo 或 CI 绿色不能独立代表用户功能完成。

每次交付说明实际改变的用户行为、对应 F/W/AC、源码与制品、验证结果、未解决风险和接下来的就绪任务。开发验收完成以 verified_target 为依据；只有实际获准并完成发布才使用 released。

最终提供完整同源制品、全部功能与证据矩阵、混合版本兼容表、部署及升级回滚手册、来源/SBOM、真实限制和残留阻塞。存在尚未完成的必交付功能或缺少必需现场证据时，如实交付候选和缺口，不宣布全量完成。继续处理所有未受阻工作，直到本任务范围全部满足或只剩明确列出的外部前置。
