# Original decoder and desktop presentation ownership

The daemon owns the real HEVC hardware decoder. Its sealed execution receipt shares the original worker's revocation and checked-join state. The desktop's original compressed H264 presentation owns a separate MF/D3D decoder. The new HEVC desktop route imports surfaces from the daemon's original decoder. A UUID, the TLS client's Prepared/Decoded/Stopped message, or a syntactically valid hardware announcement cannot convert an independent decoder into the daemon's original execution receipt.

The implemented shared-surface path keeps the original decoder in the daemon and lets the desktop present its decoded resources. This retains the current native channel owner, execution registry, format ACK and NLMF renewal fence. Its ownership requirements are:

1. Bind the mutually authenticated local TLS session to a verified destination process handle. The implemented Windows native transport reuses the original protected Tokio pipe and runs the same pinned TLS over it. It obtains the peer PID from `GetNamedPipeClientProcessId`/`GetNamedPipeServerProcessId`, retains the original `OpenProcess` handle, and checks the original TokenUser SID, desktop session and TokenStatistics authentication LUID. A PID supplied in JSON is insufficient. `VerifiedLocalPeer::export_target` now derives a private export capability from that same retained process object, with query/synchronization/handle-duplication rights. It never reopens a caller-supplied PID.
2. On the original codec worker, allocate a finite DXGI NT-handle texture ring on the exact frozen adapter. Validate every original output against its sealed format, generation and resource identity before copying that actual output into a ring slot. Export only read/presentation access to the verified peer process, with explicit handle ownership and close behavior.
3. Use the native keyed mutex/fence on both sides. Input transfer or a client acknowledgement cannot release a slot that the original GPU synchronization state does not show as consumed. Bound outstanding slots, bytes and age. A slow or abandoned consumer must stop receiving output and must not authorize replacing an unjoined owner.
4. The desktop imports the exact native texture on the same adapter and presents it through the existing native child surface. It must enforce current local authority and output deadlines; format/layout changes, logout, device loss and shutdown retire both import and export resources. Its presentation receipt remains distinct from the original decoder's execution receipt.
5. Preserve same-source hosted build provenance and separately gather physical GPU evidence for creation, import, actual fence consumption, presentation, multiple adapters, device loss, cadence and checked cleanup. A hosted parser or ledger test does not establish those facts.

The implemented first part now binds the actual pixel export path to a finite original-owner ledger. Every authenticated pixel stream admits one in-flight frame, at most 64 MiB, and the existing five-second transfer ceiling. It validates the actual decoded pixel hash against the private original execution receipt once, retains that same live fence across every asynchronous output chunk, and checks exact context, owner generation, format digest, sequence and PTS. Interrupted or invalid transfer retires the export stream. A changed execution/context requires a fresh authenticated consumer. The ledger's completion records only transferred bytes; it has no Presented state, GPU handle, caller-provided execution UUID or receipt deserializer.

This closes the gap between the receiver's pre-export receipt check and the later asynchronous IPC chunks. It does not create a DXGI shared surface or transfer a decoder. HEVC compressed-owner takeover is explicitly rejected even when the original execution is temporarily absent, so reordering preparation cannot turn a plain IPC acknowledgement into execution authority.

Windows `LocalServer::bind` retains the existing TCP listener and endpoint schema, and also accepts the native pipe for its exact runtime. New Windows clients prefer that native transport and fall back to the original TCP TLS only when no pipe exists. Access, authentication, busy or timeout errors never cause fallback. Old clients and Linux retain the TCP entry. TCP sessions have no process proof. `VerifiedLocalPeer` has no public PID constructor or serde path; it is available only after the TLS and runtime Hello checks, checks original process liveness, and shares cancellation, partial-frame failure, daemon stop, duplex-owner drop and pipe lifetime fencing. Native process tests exercise a real separate child, its original process handle after exit, frame cancellation/drop and both compatibility directions. The same-source Windows 27 tests and Linux 24 tests plus both strict checks passed on source `6cf496f`; `evidence/native-peer-process-6cf496f.json` preserves their exact limits. That run predates the later export capability and native ring.

The original HEVC worker now has an explicit shared-output command which allocates three exact NV12 NT-handle/keyed-mutex slots on its existing adapter, capped at 128 MiB total and five seconds per output. Each copy uses the actual original MF/D3D output, a bounded real GPU completion query, fresh native resource identities and a checked sequence. The original decoded receipt seals that exact private surface lease along with its pixel output. An unexported lease may be discarded locally on the original worker; once descriptor writing begins, uncertain transfer cannot take that path. Only the actual keyed-mutex return key releases an exported slot. Original peer revocation also gates execution receipts and NLMF renewal. This producer slice still requires its own hosted compilation and physical GPU execution.

`OpenNativeSharedVideo` now reserves one consumer of that original decoder under the exact current AppCore display/format ACK. A second consumer and ordinary pixel mailbox polling cannot consume the reserved output. Its one native TLS connection carries the ring and each complete frame descriptor, including original execution resource/generation, catalog hash/revision, selection sequence, signed format epoch/digest, source/layout, native sequence/PTS, slot/resource identity, actual mutex keys, resource expiry and a maximum 100 ms presentation authority deadline derived from the original View/NLMF lease. Heartbeats refresh only that current authority. Frame transfer completion is a TLS write observation. No client feedback message recycles a slot, rebinds execution or creates a Presented receipt. Closing, partial descriptor transfer, stale authority or invalid context retires the original decoder consumer.

The exclusive claim retains the original sealed execution receipt, rather than a permanent session-wide boolean. A display/format switch may reserve the new original execution only after its predecessor really retired and joined. No IPC Stopped message clears that condition. An acknowledged display whose original format/decoder is still preparing receives an explicit `SharedVideoPreparing` response; the desktop retries that exact target for a bounded two seconds rather than immediately treating it as unsupported.

The desktop GPU entry tries this original-surface route first. H264 rejects it before reserving an owner and retains its existing compressed FIFO. The successful HEVC client adopts the three actual destination NT handles once in an opaque, shared lifetime owner; frame leases retain that same handle owner and the native TLS peer proof. The importer enumerates the exact original hardware adapter and driver version, calls `ID3D11Device1::OpenSharedResource1` once per resource, validates exact NV12 geometry and shared/keyed-mutex flags, and creates no `IMFTransform`. It reuses the native child window, swapchain and SDR BT.709 video processor. Each frame acquires its actual read key; GPU conversion must complete through the bounded event query before the native return key is released. Hidden or late frames may return that key without presenting. Only actual successful DXGI Present produces the separate private submission receipt. Receiver diagnostics distinguish shared transfer and consumption from local decoding, with real worker join and native cleanup retained independently.

Destination adoption is serialized by a ring-identity lifetime registry. A second live claim shares the same owner only for the exact descriptor; another ring cannot own any of its live numeric handles. Retired ring identities remain tombstones, so an old descriptor cannot close an unrelated handle after numeric reuse. The registry is bounded to 4096 ring identities per desktop process and fails explicitly on exhaustion. The producer never uses `DUPLICATE_CLOSE_SOURCE` on an announced handle. On original-worker retirement, cleanup-only NT handles and the original retained process object enter a bounded ledger. It duplicates remote handles only into the daemon for inspection and uses actual kernel object identity comparison to distinguish the original resource from a closed/reused handle. It does not close or mutate the remote numeric value. Uncertain partial-transfer resources remain charged until those real handles close or the destination process exits: at most three current/uncertain rings per original process and eight globally, each within its 128 MiB cap. A quota failure stops that GPU route; it is not a fabricated close acknowledgement.

The sequential producer, TLS descriptor and desktop importer slices still require fresh same-source hosted compiler/strict validation. Physical allocation/import/consumption, adapter/device-loss behavior and cadence have not been accepted. The producer currently preserves its existing readback output as well as making the native shared copy; this is an implemented presentation route, not yet a zero-readback performance acceptance result. Production issuance stays disabled, physical GPU and advanced-format acceptance remain open, and the Luanti 25-second failure and its threshold remain preserved.

W32/W33 still include source implementation work beyond device acceptance. The executable HEVC contract is Main8, 4:2:0, eight-bit, SDR BT.709 limited, complete IDR access units and integer 1–120 FPS. The explicit product provider currently caps the chosen target at 1920×1080. Main10/P010 needs a real ten-bit parser/admission, original encode/decode resources and presentation conversion; 4:4:4 needs real source/codec/import surfaces; HDR needs ten-bit capture, independent color/transfer signalling, metadata and HDR output; 4K/144Hz and fractional/high-frame combinations need executable target/resource/scheduling and a qualified per-combination fallback route. The generic protocol enum/catalog alone implements none of those owners. Removing the original decoder's retained BGRA readback on the shared-only route is also remaining performance implementation work. Actual 1080p60 cadence, input/concurrent workload, device loss, multi-adapter and DPI/display-switch results remain separate missing target evidence.
