# WebRTC 累计 ICE 完成状态

原生 answerer 继续使用固定 webrtc-rs 的真实 UDP/ICE、原双签信令以及接收端的
`IceSnapshotCursor`。已签名完成的候选集合不能再增加、减少或撤回完成状态。
管理端的原权限、序号、期限、地址和路径检查保持有效。

读取当前 SDP 会等待 webrtc-rs 内部异步锁。如果先读 SDP、再读收集完成标志，
收集线程可能在两次读取之间完成，令较早的部分集合被标成最终集合。后续真正
完整的集合将违反原不可变完成契约。原生端现在先读取完成状态，再读取 SDP；
如果读取期间完成，本次仍声明未完成，下一次原轮询提交完整集合。原有非 trickle
模式仍等待原收集完成 promise，不改变期限。

浏览器首次发布的 description 是调用方此前读取的 SDP，因此其首次 trickle
快照明确保持未完成。原 pump 随后读取最新本地 SDP 并发布完成。该操作不删除
候选，也不授权新的候选、路径或 endpoint。后续 pump 同样先观察完成再读取 SDP。

新增回归使用八个真实原生 ICE peer，在实际收集期间反复读取生产适配器的快照，
用原严格累计 cursor 验证每次变化，并在完成后再次读取完整集合，要求没有新增
或删除。它不替代原 Chrome、Edge、Firefox 完整 Web/native 媒体、输入、文件与
清理验收。

原生发布过程仅记录现有 `SignalSummary` 的固定计数、完成标志、HTTP 状态及是否
为 InvalidMessage，不记录 SDP、地址、候选字符串、密钥、token 或自由错误文本。
验收 fixture 和证据 collector 分别做类型读取及白名单投影，新增反例检查畸形
类型、越界计数、布尔冒充整数和附加敏感字段都不会进入保留记录。

`f24b79f` 的 Firefox 原例确实在第一条本机信令 204 后收到第二条信令 403；
当时没有足够细的计数/错误码证据来证明具体根因。此修改修复源码中可确认的
读取竞态，须由新源码的原完整验收及新增观测进一步确认，不能倒写旧失败。
所有编译、格式、自动检查及执行均须由 GitHub 托管 Actions 完成。
